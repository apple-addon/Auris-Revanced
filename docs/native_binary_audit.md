# Native binary audit — PAWS / HiBy reference engines

Audit target: the rebranded trees under `/root/apks/paws_auris` and
`/root/apks/hibs_rebranded`, and the exact binaries packaged in
`app/src/main`. ARM64 addresses below are link-time virtual addresses for the
hashes in `docs/native_audit/packaging-arm64.json`; they are not stable APIs.
No ARM binary was executed on the x86_64 host.

## 1. Dependency repair

`llvm-nm -D --undefined-only` found **no mangled C++ imports** (`_Z…`) in any
binary carrying a `libstdc++.so` entry. `patchelf 0.18.0 --remove-needed` was
therefore used to remove the stale entry from:

- `jniLibs/{arm64-v8a,armeabi-v7a}/libsmartusb_jni.so`
- `jniLibs/{arm64-v8a,armeabi-v7a}/libusb.so`
- `jniLibs/armeabi-v7a/libhibyaudioutils.so`
- both ABI copies of `EFOSVirtualizer V1.86.so`
- both ABI copies of `EFOSpatializer V1.62.so`

`__cxa_atexit` and `__cxa_finalize` resolve from Android `libc.so`, not
`libstdc++.so`. The final dependency proof is generated by:

```sh
python scripts/verify_native_packaging.py --project . \
  --output docs/native_audit/packaging-arm64.json
```

Result: zero `libstdc++.so` entries and zero unresolved `DT_NEEDED` entries.
The allowed system set is limited to Android NDK platform libraries present on
Android 10–16.

## 2. ARM64 ELF hardening

All 12 ARM64 shared objects packaged from `jniLibs` and `assets/Plugins` have:

- every `PT_LOAD` aligned to `0x4000` (16 KiB);
- a `PT_GNU_RELRO` segment;
- immediate binding (`DT_BIND_NOW` / `DF_1_NOW`).

`liblhdc.so` originally advertised 64 KiB alignment. Its segments were already
congruent at 16 KiB, so only the two `p_align` fields were reduced to `0x4000`;
no code, offsets, or addresses moved. Current hash:
`f0982785f10e145dc46b7de96c69968a81f8eaeffca49fa6774bb4879f61c9f3`.

| Library / plugin | LOAD alignment | RELRO | NOW |
|---|---|---|---|
| libauriscore.so | 0x4000 / 0x4000 / 0x4000 | yes | yes |
| libffmpegJNI.so | 0x4000 × 4 | yes | yes |
| libffmpeg_neon.so | 0x4000 × 3 | yes | yes |
| libhibyaudioutils.so | 0x4000 × 3 | yes | yes |
| libhibyservice.so | 0x4000 × 3 | yes | yes |

## 3. PAWS `libauriscore.so`

SHA-256:
`b48e094d1f2adb371e3d461b62fe75bfc21656a1157c29126ceebaa7ac5d1524`.

`JNI_OnLoad` is at `0x21b5a8`. The binary has no exported `Java_*` methods;
registration is through `RegisterNatives` (JNIEnv offset `0x6b8`).
`scripts/audit_native_binaries.py` reconstructs relocated and stack-copied
`JNINativeMethod` tables with Capstone/pyelftools.

- 22 `RegisterNatives` vtable loads were identified (20 direct call sites plus
  two tail-call helper sites).
- 139 registered native methods across 24 `com.auris` host classes were
  cross-checked against the smali surface.
- The 20 direct sites contain 130 table entries; the remaining classes use
  obfuscated/tail-call registration helpers. Full decoded output is in
  `docs/native_audit/auriscore-jni-arm64.json`.
- `com.auris.equalizer.eq.PeqNativeUtils.getParameter(Object,byte[],byte[])`
  is declared in smali but has **no registration and no export**. It must not
  be called. The other six methods are registered.
- The original, exact host classes and callbacks are assembled from the
  rebranded smali into `assets/reference/paws_host.apk`. This avoids unsafe
  one-class shims and preserves obfuscated callback/field layouts.
  `com.auris.bridge.NativeLoader` performs `ffmpeg_neon → auriscore` loading
  from that class loader so JNI `FindClass` resolves the same host DEX.

Important recovered DSP/output entries:

```text
Pipeline2.native_create             ()J                    0x2e4d08
Pipeline2.native_build              (J ByteBuffer ByteBuffer I)I 0x2e4fa8
Pipeline2.native_request_open       (J String I byte[] III)I     0x2e5608
Pipeline2.native_route_msg          overloads               0x2e5e44…0x2e622c
PeqNativeUtils.setParameter         (Object byte[])I        0x2de050
PeqNativeUtils.setEnabled           (Object Z)I             0x2ddf44
CcPluginService.native_get_samples  (J byte[])I             0x31b488
CcPluginService.native_register     (J CcPluginService)V    0x31b67c
```

The internal graph is DSPI EQ/tone/preamp/limiter/reverb/resampler/dither/DVC,
then an output plugin. `res/xml/auraudio_builtin_plugins.xml` identifies the
real DSPI, reverb, tempo, resampler, FFmpeg/OpenMPT/WavPack/MPC decoders, and
AudioTrack/AAudio/OpenSL/Hi-Res/USB/Chromecast outputs. The native CC output
can pull processed interleaved PCM through `native_get_samples`; accepted PCM
formats are S32, Float32, and packed 24-bit. DSD has to use the PCM tap or a
native output path, not be mislabeled as raw DSD through that tap.

There is no public arbitrary-PCM `transform(ByteBuffer)` JNI export. PAWS
input opens a URI/FD and the live `Pipeline2` owns decoding/DSP/output. Any
integration must report this distinction instead of pretending a clean-room
processor is PAWS.

The plugin interface package passed by `JNI_OnLoad` is exactly
`com.auris.audioplayer`; the host DEX retains that identity. No certificate or
license check appears in the direct JNI registration sequence. The separate
`verify_apk_signature` plugin-package path is not used for in-process loading.

Dynamic exports are limited to `JNI_OnLoad`, `JNI_OnUnload`, and the native
plugin API (`pa_register_*`, `pa_alloc_plugin_context`, `pa_get_plugin*`,
`pa_send_msg`, format helpers, and internal registration setters).

## 4. HiBy `libhibyservice.so` / `libhibyaudioutils.so`

HiBy service SHA-256:
`dce9a1a682dfc76b682a69eb75226019cbe2d1a827bad038b0a4c8ca81b931fe`.

The exact JNI host DEX is `assets/reference/hiby_host.apk`; package names under
`com.hiby.music.sdk` remain unchanged. Its loader performs
`usb → smartusb_jni → hibyaudioutils → hibyservice`.

Static exports: `JNI_OnLoad` plus 41 JNI functions (8 `OtHiByTrackUtils`, 21
`DspUtil`, 4 `PinyinUtil`, and 8 `SaImageParser`). Seven `RegisterNatives`
sites add 58 methods:

- `SmartAv`: 45;
- `VUTools`: 3;
- `JniThreadPoolWorker`: 1;
- `AudioUtils`: 1;
- `AudioUtilsHiRes`: 1;
- `SmartLHDC`: 3;
- `SmartUAT`: 4.

SmartAv's smali also declares `native_getLyric` and
`native_get_usbdevice_type`, but neither is registered/exported in this binary;
they are excluded from the bridge contract. See
`docs/native_audit/hibyservice-jni-arm64.json`.

### Real MSEB / PEQ controls

Built-in `MSEB` and `PEQ Combined` modules and their native parameter handlers
are present in `libhibyservice.so`; no external `libmseb.so` or `libpeqc.so` is
required by these built-ins.

MSEB uses `DspUtil.OnDspAdd("MSEB")` and `SetDspInfoInt/Float` keys:

```text
master_temp, bass0, bass1, thickness, vocal, female,
male_vocal, female_vocal, instruments, air, preamp
```

The corresponding `mseb_`-prefixed keys used by the original preference layer
are preserved by the bridge. Native slider range is -100…100 and preamp is
-45…45 dB.

PEQ uses `SmartAv.native_setObjectAttr` / `native_setPeqValue` with:

- `peq_global_param`: `[enable, preampDb, en_preamp]`;
- `peq_param`: `[index, enabled, frequencyHz, gainDb, q, type]`;
- `peq_response` for native response data;
- `peq_param_set_pregain`, `peq_param_set_qvalue`, `peq_param_set_gvalue`,
  `peq_param_set_fvalue`, and `peq_param_set_channel` for individual updates.

The native PEQ response/configuration code is real HiBy code. No Kotlin biquad
is presented as HiBy.

### PCM and output limits

`OtHiByTrackUtils` is the decoded-PCM handoff:

```text
createTrack(sampleRate, channels, sampleSize, formatType)
write(byte[], byteCount)
streamStart/streamEnd/release/destruct/latency/nowConsumed
```

It is a native output sink, not a transform returning PCM. `DspUtil` configures
the live global chain and also has no `process` export. `SmartAv.onData` can
capture native output into a Java byte array, but it is copy-out and cannot
modify the audible buffer. `AudioUtilsHiRes.nativeSetDirectBuffer` is a real
zero-copy output buffer only while SmartAv owns the output.

`libhibyaudioutils.so` exports only `java_hibyaudiodevice_util_init` and
`notifyEvent`; it contains no PCM processing entry point.

The original hard-coded `/data/user/0/com.hiby.music/...` default is not used:
the host context supplies this app's private `files/Plugins` directory.
Plugin assets are extracted there before `DspUtil.init`.
